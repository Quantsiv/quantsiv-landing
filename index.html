Harvest Now, Decrypt Later

The breach has already happened. We just cannot read it yet.

The attack is storage, not computation

An adversary does not need a quantum computer today. They need only to record your encrypted traffic and exfiltrated data now, then decrypt the archive once a cryptographically relevant quantum computer exists. RSA, ECDSA, Diffie-Hellman and DSA all fall to Shor's algorithm. For crypto-asset wallets the ledger is the archive: a public key already on-chain is enough to forge a transfer later.

The real deadline is your data's lifetime

What matters is not when the quantum computer arrives, but how long your data must stay secret. A system with a 25-year confidentiality requirement is already compromised if its traffic was captured yesterday. Health records, financial data, government communications and trade secrets are all in scope today.

AI-written code can add quantum-vulnerable defaults

Code assistants pick cryptographic primitives by pattern completion, and they can reproduce quantum-vulnerable defaults. The code compiles and passes tests, and it is still quantum-vulnerable.

The Deadline Is Already Set

This is not a speculative timeline. Standards bodies and governments have published dated migration guidance and requirements.

  1. 13 Aug 2024

    NIST publishes the post-quantum standards

    FIPS 203 (ML-KEM) for key establishment, FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA) for digital signatures. The replacement algorithms now exist.

  2. Nov 2024

    NIST IR 8547 proposes the deprecation clock

    In the initial public draft, 112-bit-strength RSA, ECC and DH, such as RSA-2048, are deprecated after 2030. All quantum-vulnerable public-key algorithms, including P-256, are disallowed after 2035.

  3. 22 Jun 2026

    Executive Order 14412 names the threat

    The order addresses the harvest-now, decrypt-later threat. It sets 31 Dec 2030 for post-quantum key establishment and 31 Dec 2031 for signatures on high-value assets and high-impact systems.

  4. 24 Jun 2026

    OMB M-26-15 sets the federal migration phases

    Five phases from 2026 to 2035. Agencies build an automated inventory whose data "should populate a central Cryptographic Bill of Materials". Agency plans are due 22 Oct 2026.

  5. ~Mar 2027

    CBOM minimum elements published

    CISA, in coordination with NIST, publishes guidance on CBOM minimum elements within 270 days of EO 14412, about Mar 2027.

  6. 2030 – 2035

    Migration deadlines run to 2035

    Under EO 14412, key establishment by 31 Dec 2030 and signatures by 31 Dec 2031 on high-value assets and high-impact systems, with a proposed FAR rule for covered contractors. NSA CNSA 2.0 sets exclusive-use dates between 2030 and 2033, depending on the category. In the EU, the NIS Cooperation Group roadmap (23 Jun 2025, a recommendation) asks for national strategies by end-2026, high-risk use cases by end-2030 and as many systems as feasible by 2035.

Sources: EO 14412, OMB M-26-15, NIST IR 8547, CISA Post-Quantum Cryptography Initiative, NSA CNSA 2.0, NIST FIPS 203, EU NIS Cooperation Group roadmap.

How Quantsiv Works

From scanning your code to a CycloneDX 1.6 CBOM

1. Discover

Quantsiv scans for cryptographic usage in source code, key and certificate files, CI scripts and TLS endpoints you name or verify. Scanning runs in your CI by default. Only the CBOM and finding metadata reach Quantsiv, and only if you upload.

2. Analyze

Each finding is evaluated against the quantum-vulnerable algorithms - RSA, ECDSA, Diffie-Hellman, DSA - and ranked on two tracks: harvest-now-decrypt-later exposure for encryption and key establishment, based on how long you declare the data must stay confidential, and a separate track for signatures against the signature deadline.

3. Prioritize

Results are ranked so remediation follows business risk rather than raw finding count. A long-lived health record and a short-lived session token are not the same exposure, even when both use RSA. Each finding carries the reason for its rank and, where the use is clear, the standard to migrate to.

4. Prove

Export a CycloneDX 1.6 CBOM, SARIF and a ranked report. Each build is compared with the latest default-branch build, and the change check flags cryptography the change adds, so the migration does not regress.

Capabilities

Detects common cryptographic APIs in Python, JavaScript and TypeScript, Go, Java and Kotlin, C#, Rust, Ruby, PHP, C and C++, Objective-C, Swift and Dart, openssl, ssh-keygen and keytool commands in CI and shell scripts, and keys and certificates in PEM and SSH formats. Pattern-based, so depth varies by language and some calls are missed.

Cryptographic Bill of Materials

CycloneDX 1.6 that passes the schema's strict validation. Import a CBOM from any producer and export the whole estate as one.

Lifetime-aware ranking

Declare how long each kind of data must stay confidential. Encryption and key exchange are ranked by that lifetime. Signatures are tracked separately against the signature deadline, because their risk is forgery, not retroactive decryption.

Change check

Compare each build with the latest default-branch build and flag the cryptography a change adds. Set policy per data class and record exceptions with a named approver and an expiry. Results go to Code Scanning as SARIF and, with the GitHub Actions template, to the pull request as a comment.

Runs in your CI

A container with templates for GitHub Actions, GitLab, Jenkins and Azure DevOps. Scanning works offline. Only the CBOM and finding metadata reach Quantsiv, and only if you upload.

Keys, certificates and TLS

Reads key and certificate files for algorithm and size. Probes the TLS endpoints you name; the hosted service probes only domains you prove you own with a DNS record.

Wallet and custody code

Finds secp256k1 and Ed25519 signing keys, Schnorr signatures, and ECDH and ECIES key transport in common wallet libraries. Once a wallet's public key is on-chain its risk is forgery, not decryption, and its guidance says what to do until the chain accepts post-quantum signatures. Reads code, not the chain.

For coding assistants

A read-only MCP server lets an AI coding assistant ask your policy and declared lifetimes before it writes cryptography. The same check runs at the gate. It has no write tools and no model of ours in it.

Migration guidance

Where the use is clear, each finding names the standard to move to: ML-KEM (FIPS 203), ML-DSA (FIPS 204) or SLH-DSA (FIPS 205), with hybrid key exchange during the transition.

Honest limits

Pattern matching misses aliased and dynamic calls, vendored code and dependencies. We state the limits up front.

Roadmap

Sequenced to land capability ahead of the deadlines that force the migration.

Phase 1 · Now → 2027

Audit

Deploy into CI pipelines and map the cryptographic footprint of each application.

  • Pipeline integration for push and pull request scans
  • Footprint mapping across source code, key and certificate files, CI scripts and TLS endpoints
  • HNDL-specific vulnerability identification and prioritization
  • CBOM output aligned to the CISA minimum elements once published, about Mar 2027
  • JavaScript and TypeScript, C and C++, Swift and Dart; container and cloud inventory later
Phase 2 · 2027 → 2028

Migrate

Close the loop from finding to fix with suggested changes and hybrid cryptography.

  • Suggested changes as draft pull requests with the diff, rationale and cited authority, for a person to review
  • Hybrid ciphers running classical and post-quantum algorithms in parallel
  • Validation suites that check updates do not break functionality
Phase 3 · 2028 → 2030

Agentic Crypto-Agility

Scale to distributed enterprise estates. Agents propose; deterministic checks verify; a person approves. Nothing merges or deploys on its own.

  • Crypto-agile architecture across clouds, PKI, KMS and service meshes
  • Agents that propose a PQC algorithm for each use case, for a person to approve
  • Deterministic verification of approved migrations before anything merges
  • Crypto-agility scorecard measuring migration readiness
Phase 4 · 2030 → 2035

Platform Consolidation

One deployable unit covering audit, migration and optimized post-quantum cryptography.

  • Dedicated cryptographic research team
  • Implementations of the standardized primitives, shipped only once validated under FIPS 140-3
  • All-in-one product consolidating audit, migration and review
  • Managed PQC service; SOC 2 and ISO 27001 as long-term goals
